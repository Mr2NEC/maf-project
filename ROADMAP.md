# maf-project: план розвитку

_Аналіз станом на 2026-09-22. Останній коміт — червень 2025._

## Поточний стан

**Що це:** платформа для клубів спортивної мафії: клуби, майданчики, гравці, ігри з типами,
ролями та діями, публічний сайт.

| Частина | Стек | Стан |
| --- | --- | --- |
| Бекенд | NestJS 11, GraphQL (Apollo, code-first), TypeORM, MySQL 8, JWT + argon2 | 17 модулів з CRUD, реєстрація та вхід. Ігрової логіки немає |
| Фронтенд | Next.js 15, React 19, next-intl (uk/en), Tailwind, shadcn/ui, Storybook | Каркас: хедер, тема, перемикач мови. **Усі 8 сторінок порожні**, з API не з'єднаний |
| Інфраструктура | Docker Compose (dev/prod), makefile | Є dev-оточення; prod-конфіг не в git |
| Якість | ESLint, Prettier | Тестів немає (лише шаблонний e2e), CI немає |

### Незакомічена робота
Міграція на **next-intl v4 + Next 15.3** (13 змінених і 3 нові файли) лежить незакоміченою з
червня 2025. Її треба або завершити, або відкотити — це перший крок.

### Знайдені проблеми

**Безпека (критично перед будь-яким деплоєм)**
- JWT-гард стоїть лише на `updateUser`. Решта мутацій відкрита для всіх:
  `removeUser`, `createGame`/`deleteGame`, CRUD клубів, ролей тощо, а також `initializeDatabaseClubs`,
  яка завантажує дані з зовнішнього URL і пише файли на диск.
- `RolesGuard` і `@Roles` написані, але ніде не використовуються.
- `updateUser(id)` не перевіряє, що користувач змінює саме себе.
- Запит `users` без авторизації віддає email усіх користувачів.
- Дефолти в конфігах: `JWT_SECRET || 'secret'`, `MYSQL_PASSWORD || 'password'`. Якщо змінна
  середовища не задана, застосунок мовчки стартує з небезпечними значеннями.
- `email` не має unique-обмеження → можна зареєструвати дублікати.
- Вхід із неіснуючим email повертає «Entity not found», а з неправильним паролем —
  «Invalid Credentials». За різницею відповідей можна з'ясувати, які email зареєстровані.
- `signup` приймає `clubId`, тобто будь-хто може одразу вступити в будь-який клуб.
- `console.log` з `userId` у `JwtStrategy`.

**Архітектура та дані**
- `synchronize: true` замість міграцій. Для продакшну це ризик втрати даних.
- Немає DataLoader: зв'язки в GraphQL підтягуються масивами `relations`, що дає N+1 запитів і
  перевантаження на списках.
- Немає пагінації в жодному списку.
- `Player.username` дублює `User.username`.
- Сервіси дублюють перевірки (`findOne` вже кидає 404, а далі код знову перевіряє `!game`).

**Інфраструктура**
- `docker-compose.prod.yml` у `.gitignore`, тож прод-конфігурація не версіонується.
- Кореневий `package.json` посилається на видалений `docker-compose.dev.yml`.
- `node_modules` на хості неповні (не запускаються навіть `tsc`/`eslint`), тож усе працює
  лише в Docker.
- Немає `.env.example`.
- Залежностям 15+ місяців.

### Етап 1. Безпечний і надійний бекенд (1–2 тижні)
**Авторизація**
- [ ] Глобальний `GqlJwtGuard` + декоратор `@Public()` для відкритих запитів (список ігор, клубів, рейтинг)
- [ ] Глобальний `RolesGuard`; усі адмінські мутації — `@Roles(UserRole.ADMIN)`
- [ ] Перевірка власника: користувач змінює лише свій профіль, власник клубу — лише свій клуб
- [ ] Ролі користувачів розширити: `user`, `host` (ведучий/суддя), `club_admin`, `admin`
- [ ] Однакова помилка входу для неіснуючого email і невірного пароля
- [ ] Прибрати `clubId` із `signup`; вступ до клубу — окремий процес із підтвердженням
- [ ] Refresh-токени в httpOnly cookie; access-токен короткий
- [ ] Обмеження частоти запитів (rate limit) на `signIn`/`signup`

**Конфігурація та дані**
- [ ] Валідація env при старті (Joi або zod), без небезпечних дефолтів
- [ ] Міграції TypeORM замість `synchronize`; сіди для довідників (типи ігор, ролі, дії)
- [ ] Unique на `users.email`, індекси на зовнішні ключі
- [ ] `initializeDatabaseClubs` перенести в CLI-скрипт/сід, прибрати з публічного API

**GraphQL**
- [ ] DataLoader для зв'язків замість `relations`
- [ ] Пагінація (cursor або offset) для всіх списків
- [ ] Не віддавати `email` у публічному типі `User`
- [ ] Обмеження глибини/складності запитів
- [ ] Єдиний формат помилок з кодами; логер (pino) замість `console.log`

**Тести**
- [ ] Unit-тести сервісів (auth, games, players)
- [ ] e2e-тести GraphQL на тестовій БД (testcontainers)

### Етап 2. Ігровий рушій — ядро продукту (2–4 тижні)
Зараз гра — це лише запис зі статусом. Потрібна доменна логіка:
- [ ] Зафіксувати правила: який регламент (ФІІМ / клубний), склад ролей для 10 гравців
- [ ] **Машина станів гри:** `waiting → seating → night(N) ⇄ day(N) → finished`, з явними
      дозволеними переходами
- [ ] Реєстрація гравців на гру, розсадка, роздача ролей (випадкова або ручна ведучим)
- [ ] Валідація дій: дія дозволена ролі (`RoleAction`), фазі та раунду; гравець живий
- [ ] День: висунення кандидатур, голосування, автокатастрофа, промови
- [ ] Фоли, дискваліфікації, «найкращий хід»
- [ ] Автоматичне визначення перемоги та підсумок гри
- [ ] Нарахування балів за гру (основні та додаткові) згідно з регламентом
- [ ] Панель ведучого: GraphQL subscriptions для оновлення в реальному часі
- [ ] Доменну логіку тримати в чистих функціях, щоб її було легко покрити тестами

### Етап 3. Фронтенд MVP (2–3 тижні, частково паралельно з етапом 2)
- [ ] GraphQL-клієнт + **graphql-codegen** (типи з `schema.gql`)
- [ ] Автентифікація: вхід, реєстрація, сесія через httpOnly cookie, захищені маршрути
- [ ] **Гравці:** список із пошуком, профіль гравця (статистика, історія ігор)
- [ ] **Календар:** майбутні ігри, запис на гру
- [ ] **Рейтинг:** таблиця з фільтрами за періодом і клубом
- [ ] **Панель ведучого:** ведення гри в реальному часі (зручна на планшеті)
- [ ] Головна, «Про нас», «Контакти» — статичний контент
- [ ] Стани завантаження та помилок, SEO-метадані для кожної сторінки, переклади uk/en

### Етап 4. Клубні функції (3–4 тижні)
- [ ] **Турніри:** сутність, етапи, розсадка за турами, підсумкова таблиця

- [ ] Клуби: сторінка клубу, учасники, розклад, адмінка власника клубу
- [ ] **Блог:** MDX або headless CMS — не варто писати свою CMS
- [ ] Завантаження файлів (аватари, логотипи) в S3-сумісне сховище замість локальної папки

### Етап 5. Продакшн (1 тиждень)
- [ ] Версіонувати `docker-compose.prod.yml`, секрети — лише з env
- [ ] Виправити розбіжності prod-конфігу: у `.env.prod` є `MYSQL_NAME` і `JWT_EXPIERES_IN`,
      а compose чекає `MYSQL_DATABASE` і `JWT_EXPIRES_IN`; порт бекенду `5000:3000`, хоча застосунок

- [ ] Бекапи MySQL за розкладом, перевірка відновлення

## Рішення, які потрібно ухвалити

1. **Регламент гри:** ФІІМ чи власні правила клубу? Від цього залежать етап 2 і формула рейтингу.
2. **Головний користувач першої версії:** ведучий, який веде гру (панель ведучого), чи гравець,
   який дивиться рейтинг і календар? Від цього залежить порядок етапів 2 і 3.
3. **Один клуб чи багато:** платформа для багатьох клубів вимагає ізоляції даних і ролей на рівні клубу.
4. **Хостинг:** VPS + Docker чи хмарний сервіс (фронт на Vercel, бекенд і БД окремо)?
